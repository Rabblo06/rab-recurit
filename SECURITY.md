# Security

## Reporting a vulnerability

Please report security issues privately — not as a public GitHub issue.

- Preferred: use GitHub's [private vulnerability reporting](../../security/advisories/new) for this repo (Settings → Security → "Report a vulnerability" — enable it if you don't see this link yet).
- Fallback: email sebastiansiju1804@gmail.com with subject `SECURITY: rab-recurit`.

Use the finding format from `rab-workforce-architecture.md` §5.8: severity, actor → action → consequence, file:line, root cause, fix, regression test. Never write "consider improving security" in place of a finding.

**Response time:** we aim to acknowledge reports within 3 business days and provide an initial assessment (valid/invalid, severity) within 7.

## Supported versions

There is no released/tagged version yet, so only `main` (what production deploys) is supported. A versions table will be added once releases start. Work on unmerged feature branches (for example `feat/twenty-parity-foundation`) is not supported.

Nothing above is ever committed. `.env.example` at each package root carries variable names only, never values. `gitleaks` runs in `ci-security.yaml` and blocks merge on a detected secret.

## Authentication and session policy (implemented; verified against the code on 2026-10-23)

These values are the code's defaults. Each env-tunable value names its variable. The user-facing version is
`packages/rab-docs/security/authentication-and-sessions.mdx`, and the developer version is
`packages/rab-docs/developers/authentication-flow.mdx`.

**Session lifetimes** (`engine/core-modules/auth/session-policy.ts`; tests `session-policy.spec.ts`,
`token/retention-policy.spec.ts`). The idle timeout is re-evaluated from the CURRENT roles on every request, so a
promotion tightens it at once. The absolute lifetime is fixed when the session is created.

| Session class | Idle timeout | Absolute lifetime |
|---|---|---|
| Platform administrators (any target, any role) | 30 minutes | 24 hours |
| Manager-tier roles (`manager`, `ceo`, `org_admin`, `super_admin`, `admin`) on any target, mobile included | 30 days | 180 days (owner decision 2026-10-14, Twenty parity) |
| Mobile workers (`staff_app`, `venue_manager_app`) | 7 days | 90 days |

- **Access JWT:** 15 minutes, HS256, `{sub, org, roles, sid}` plus `kid`, and never longer than the session.
  Permissions are never read from it: they are resolved server-side per request.
- **Refresh token:**
  - opaque, stored only as SHA-256;
  - 30 days per row, capped by the family's absolute deadline;
  - rotated on every refresh. Presenting a rotated or revoked token revokes the whole family (`RefreshTokenReuseError`).
  - Dead rows are kept for **181 days** (`core.worker_cleanup_auth_tokens`, `WebSessionRetention1786717100000`,
    `AUTH_TOKEN_CLEANUP_RETENTION_DAYS`). That is one day longer than the longest session, so reuse evidence outlives
    every live family.
- **Per-request liveness:** every authenticated request re-checks in PostgreSQL, on the database clock:
  - the session's family is not revoked;
  - it is within its absolute and idle deadlines;
  - its security version still matches (`SessionValidityService`, `AuthSecuritySnapshotService`).

  An access token from a revoked session is refused on its next request, not when it expires.

**Revocation.** Each of these ends sessions immediately, and the next request gets 401:
- signing out (that session);
- revoking one device, or "Log out all other devices";
- a password change or reset (all the user's sessions);
- suspending or deactivating the account, or suspending the organisation (the security version is bumped);
- turning password sign-in off for an organisation (password sessions only; SSO sessions and the exempt mobile
  workforce are kept, D-A2);
- turning MFA on (every OTHER session of the account);
- an administrator's MFA reset (all the target's sessions);
- a completed cross-host login handoff (the source session).

**Sign-in limits** (`auth/services/login-attempt-limiter.service.ts`, Redis token bucket, keys hashed; test
`login-attempt-limiter.integration.spec.ts`). The limits are checked before any account lookup, so unknown and real
addresses behave the same:
- **Per (email, IP):** a burst of `AUTH_LOGIN_EMAIL_IP_BURST`=5 refilling over `AUTH_LOGIN_EMAIL_IP_WINDOW_SECONDS`=900,
  and `AUTH_LOGIN_EMAIL_IP_DAILY_LIMIT`=30 per 24 h.
- **Account-wide:** a burst of `AUTH_LOGIN_ACCOUNT_BURST`=50 per `AUTH_LOGIN_ACCOUNT_WINDOW_SECONDS`=900. This applies
  only to addresses that have not signed in to the account in the last `AUTH_LOGIN_KNOWN_IP_TTL_DAYS`=30.
- **Refusal:** 429 `LOGIN_RATE_LIMITED` with Retry-After. Nothing is locked indefinitely: the old per-email "10 in
  15 min" hard lockout was removed (D-A1).
- **Fail closed:** if Redis is unavailable, sign-in is refused with 503 `RATE_LIMIT_UNAVAILABLE`.
- **Route throttles (per IP) also apply:** 5 per minute on login, refresh, forgot-password, reset-password and account
  activation; 10 per minute on the MFA challenge routes.

**MFA** (wave 4, `auth/mfa/`, `auth/services/mfa-*.service.ts`; tests `mfa-totp-wave4`, `mfa-attempt-limiter-wave4`,
`login-second-factor-gate`):
- **Enrolment:** TOTP (RFC 6238) with 10 single-use recovery codes. Any web user can enrol
  (`AUTH_MFA_ENROLMENT_ENABLED`=true).
- **Sign-in:** an enrolled user is always challenged on web sign-in. Such a sign-in answers `409
  SECOND_FACTOR_REQUIRED` and issues no session until `/auth/mfa/challenge/verify` succeeds.
- **Challenge limits:** a challenge lasts `AUTH_MFA_CHALLENGE_TTL_SECONDS`=300, is single use, and allows
  `AUTH_MFA_CHALLENGE_MAX_ATTEMPTS`=5 attempts. Each user also has a burst of `AUTH_MFA_USER_ATTEMPTS_BURST`=10 per
  900 s across all challenges and step-ups. Codes cannot be replayed.
- **Enforcement:** every flag defaults to **off**: `AUTH_MFA_ENFORCE_PLATFORM_ADMIN`, `_ORGANISATION_OWNER`,
  `_INITIAL_MANAGER` and `_OTHER_WEB_USERS`.
- **Mobile:** mobile sign-ins are **not** challenged (`AUTH_MFA_MOBILE_POLICY`=exempt).
- **Managing MFA:** turning it off or regenerating codes always needs the password and a current code.
- **Step-up:** a grant lasts `AUTH_STEP_UP_WINDOW_SECONDS`=300. The older password-only step-up actions still accept
  the password alone unless `AUTH_STEP_UP_MFA_FOR_LEGACY_ACTIONS`=true.
- **Admin reset:** a platform administrator can reset another user's MFA. The reset is audited and revokes the target's
  sessions.

**Key separation** (wave 2, `secret-encryption/keyring.util.ts`; see the secrets table above):
- Each key role is derived from `APP_SECRET` by HKDF under its own purpose label, unless a dedicated key is configured.
- Access tokens are signed with kid `derived-v1`, or with `APP_JWT_ACTIVE_KID` from `APP_JWT_SIGNING_KEYRING`.
- Tokens under raw `APP_SECRET` (`legacy` or kid-less) are only *verified*, and only while
  `APP_JWT_LEGACY_VERIFY_ENABLED`=true (the default).
- Boot refuses a secret reused across roles, and weak keys in production.
- `APP_KEY_SEPARATION_REQUIRED`=true (default false) refuses to boot unless a dedicated JWT keyring and cache MAC key
  are configured and legacy verification is off.

**Cookie policy** (`auth/constants/auth-cookie-policy.ts`, the only place cookie names and attributes are decided):
- **Web console:** the credential is the HttpOnly session cookie `crewflow_session` (Path=/rest/v1). The refresh
  cookie is `rab_rt` (HttpOnly, Path=/rest/v1/auth).
- **Attributes:** both are `Secure` in production. SameSite is None in production (cross-site API) and Lax in
  development. The OAuth transaction cookie is always Lax.
- **`__Host-` prefix:** with `AUTH_COOKIE_HOST_PREFIX_ENABLED`=true (default **false**), the same names carry the
  `__Host-` prefix (Secure, Path=/, no Domain).
- **Migration:** `/auth/refresh` migrates legacy cookies to `__Host-` once, under `AUTH_COOKIE_LEGACY_MIGRATION_ENABLED`
  (default true).
- **Tossed cookies:** a duplicated session cookie is refused.
- **Mobile apps:** a Bearer access token, plus a refresh token held in device secure storage.

**CSRF and origin trust** (`auth/guards/cookie-csrf.util.ts`):
- **Unsafe cookie requests:** every unsafe cookie-authenticated request must carry an `Origin` on the allow-list
  (`CORS_ORIGINS`). A missing Origin is refused.
- **Credential-issuing routes** (`/auth/login`, `/auth/refresh`): these accept JSON only. A present Origin must be
  trusted.
- **Workspace origins:** `<label>.<WORKSPACE_BASE_DOMAIN>` origins are trusted only with
  `WORKSPACE_SUBDOMAIN_ORIGIN_TRUST_ENABLED`=true, and only as the canonical origin of a READY workspace in the
  registry. Reserved labels, `xn--` labels and other ports are never trusted, and production requires https.

**Host routing trust model** (wave 3, `engine/core-modules/workspace-host/`; flag `WORKSPACE_HOST_ROUTING_ENABLED`,
default **off**, on in dev):
- **Request host:** taken from `Host`. `X-Forwarded-Host` is used only when the socket peer is in
  `TRUSTED_PROXY_CIDRS`, and a multi-valued one is refused.
- **Label resolution:** only through `core.resolve_workspace_by_host_label`. The cache lasts at most 60 s and is
  invalidated on rename, READY/FAILED and organisation suspension.
- **No authority from the host:** the host must AGREE with the session's workspace. Otherwise the request gets 404
  `WORKSPACE_HOST_MISMATCH`.
- **Reserved labels:** served as the default host, and never trusted.
- **Cross-host login handoff** (`AUTH_LOGIN_HANDOFF_ENABLED`, default off; on in dev):
  - A sign-in on a host other than the user's canonical workspace host issues no session there. It returns a
    single-use 256-bit handoff, stored as SHA-256 and valid for `AUTH_LOGIN_HANDOFF_TTL_SECONDS`=30.
  - The handoff is bound to that workspace host and is exchanged there, with a trusted Origin. The exchange revokes
    the source session.
  - A handoff presented on the default host or an unknown host is refused before lookup and is not consumed.

## What's covered so far

- **Row-Level Security:**
  - Every tenant table gets ENABLE + FORCE + `USING`/`WITH CHECK` in the migration that creates it.
  - 15 pre-auth tables are ENABLE but NOT FORCE, all owned by the NOLOGIN `rab_secure_owner`. The authoritative list
    is `NOT_FORCED_ALLOWLIST` ∪ {`organisation`, `platform_admin`} in `tools/check-rls-coverage.ts`.
  - Every `workspace_<uuid>` schema is fully forced.
  - The `check-rls-coverage` gate passes on the test DB (62 core + 21 workspace tables).
  - `db-security-posture` checks the posture golden snapshot.
- **Five enforcement layers:** guard → service → org-scoped query → RLS → staff/venue predicate. Abuse-case suites
  cover tenancy, IDOR (404 not 403), mass assignment and state machines (see THREAT-MODEL.md).
- **Authentication:**
  - argon2id (m=19456, t=2, p=1), with uniform timing and messages for unknown emails.
  - Cookie-first web sessions, rotating refresh tokens with family reuse detection, and per-request session liveness.
  - The limiter, MFA, key separation, cookie policy and host routing described above.
- **Audit:** `core.audit_log` is insert-only at the grant layer, and a trigger refuses identities from another
  organisation (foundation fix P1).
- **Configuration:** env validation fails closed on boot: missing `APP_SECRET`, `DATABASE_URL` or `REDIS_URL`; unsafe
  flag combinations; reused or weak keys.
- **Reconciled audit:** VULN-001–004 are fixed, with code and test evidence. See `SECURITY_AUDIT.md` → "Status
  reconciliation (2026-10-23)".

## Known gaps / not enabled by default

- **MFA:** the enforcement flags are off, and mobile sign-ins are not challenged (`AUTH_MFA_MOBILE_POLICY=exempt`). The
  owner decisions are open in `WAVES_4_5_VALIDATION_REPORT.md` §7.
- **Key and cookie hardening:** `__Host-` cookies, mandatory key separation and `APP_JWT_LEGACY_VERIFY_ENABLED=false`
  are off by default. Each is an owner decision per environment.
- **Host routing and the login handoff:** on in dev only. The production compose keeps them off until the production
  rehearsal.
- **Dependency advisories:** nx and picomatch (build tooling only) have not been re-verified since 2026-08-20.

New controls get a row or a bullet here in the same PR that lands them, not after.
