## Images and processes

`packages/rab-docker/rab/Dockerfile` (Node 24 Alpine, no browser) builds ONE application image, which the API and the Worker run with different commands; it includes the Worker-only packages, including the native PDF renderer. The image contains no browser: the build fails if Chromium is installed, and the image gate fails if Chromium, Playwright or any library only Chromium pulled in comes back. Both builds fail if Node or libexpat is below the minimum versions in `packages/rab-docker/rab/security-floors.env`.

The three operations commands (`containment:suspend-test-accounts`, `user-session:backfill`, `hws:backfill`) have no service of their own. Like `bootstrap-admin`, each run is a one-off container of the API service (`run --rm --no-deps rab-api node packages/rab-server/dist/command/main.js <command> ...`), from the same image and under the same owner login `crewflow_owner`; any other login is refused. Every run takes the operator label flags (`--operator "<name>"` and `--change-ref <ref>`), the per-run production authority, a host directory for its files and a kept copy of its output. The procedure is in `packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md`, section 7, "Operations commands". There is no separate operations container any more. Of its old variables, the five retired names are refused in every process, and the compose lint refuses the whole `CREWFLOW_OPS_*` / `PG_OPS_*` prefix.

| Service | Command | Database login | Notes |
| --- | --- | --- | --- |
| API | `api-prestart.sh` (then `main.js`) | the one owner login | Migrates on start under the migration lock (O3, like Twenty; approval mode `none`), registers the BullMQ job schedulers, then serves. One instance, deployed stop-then-start. Never bootstraps an admin. |
| Worker | `node packages/rab-worker/dist/main.js` (the same image as the API) | the one owner login | One non-root process (uid 1000) under the container init; workspace provisioning runs in-process. The former launcher and its provisioner child are retired (O1). |
| (no release step) | | | O3 removed the one-off `rab-migrate`: the API migrates on start, and the Worker never migrates and only consumes the job schedulers. Back up before every upgrade (`packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md` section 3). |

The database is one setting, `PG_DATABASE_URL` in `compose.env`: your PostgreSQL's admin URL (16, 17 or 18), an existing `crewflow_owner` URL, or unset for the bundled `db` service (then only `PG_DATABASE_PASSWORD`). There is no SQL, `psql` or setup command. Only the one-shot `db-setup` service receives it: it creates `crewflow_owner` if missing, with a random password it stores in a file on its own volume and reuses on every start (an existing `crewflow_owner` URL is used unchanged), and writes a credential-free target file. The API and the Worker never receive a database URL; they build the `crewflow_owner` URL from the target file and the password file, both mounted read-only. `APP_SECRET` is never part of a database credential. Production refuses the legacy names (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `DATABASE_DIRECT_URL`, `DB_POOL_MAX`) and requires TLS verify-full on a direct (non-pooled) endpoint. The image's default `CMD` is `api-prestart.sh`, which never migrates. Migrations run only in the one-off `rab-migrate` step, which takes the migration lock and checks the target, the deployment identity, the identity and, for production, the reviewed approval list (`production-migration-approval.ts`, finding N1). Full procedure: `docs/runbooks/database.md`.

Runtime guards refuse to boot the API or Worker when:

- `DATABASE_URL_UNPOOLED`, `CREWFLOW_MIGRATION_*`, `CREWFLOW_PROVISIONER_DATABASE_URL` or a bootstrap password is present
- in production, a legacy database variable (`DATABASE_URL`, `DATABASE_DIRECT_URL`, `DB_POOL_MAX`) or a libpq variable is set, TLS is weaker than verify-full, or the database's deployment identity marker does not match `CREWFLOW_DEPLOYMENT_ENVIRONMENT` / `CREWFLOW_DEPLOYMENT_ID`
- the login is anything other than `crewflow_owner`, or (in a deployment) any `PG_DATABASE_URL` reaches them at all
- `NODE_ENV=production` is set without `RAB_RUNTIME_ENV=production`

| File | Where | Topology |
| --- | --- | --- |
| `packages/rab-docker/docker-compose.production.yml` | Production: OpenShip on an Oracle VPS (arm64). The database is a managed PostgreSQL provider, the web console is on Vercel. | `rab-api`, `rab-worker` (bundle), `rab-redis`, plus the one-off `rab-migrate` release step they wait for. HWS runtime routing is off until the production rehearsal. |
| `packages/rab-docker/docker-compose.qa.yml` | Local, isolated manual QA | Mirrors the production topology (restricted logins, Worker bundle, S3 storage through MinIO, HWS off, explicit migrations), with a local database and loopback-only ports. |
| `packages/rab-docker/docker-compose.yml` | Local development | Same services. HWS is on, for development only. |

Workspace provisioning in production runs in the Worker's provisioner process. Server-path provisioning, where the API calls `core.provision_workspace` (migration `1786719500000`), is not yet approved for production. Until it is, a new workspace is built by the provisioner.

The operational procedure (per-service environment variable names, migration phases, rollback) is in the production release runbook. Values are never committed.

**Render is retired.** `render.yaml` was removed on 2026-10-23: it described the pre-cutover database roles and migrated at start, which the current guards refuse. Removing the file does not stop any Render service that still exists. Suspend or delete those services in the Render dashboard.

## Environment

Set every required variable in the hosting platform's secret store. See [Environment configuration](/developers/environment-configuration). The API and the Worker need the same application settings, including the same `APP_SECRET`. Neither receives `PG_DATABASE_URL`: it goes to the one-shot `db-setup` service only. Only the Worker additionally takes `CREWFLOW_PROVISIONER_DATABASE_URL`, which the launcher hands to the provisioner process alone as its `PG_DATABASE_URL`. The `rab-migrate` step takes only `.env.migrate` (template `packages/rab-docker/.env.migrate.example`).

Set `CREWFLOW_PROVISIONER_ENABLED` explicitly on the Worker:

| Value | Worker runs | `CREWFLOW_PROVISIONER_DATABASE_URL` |
| --- | --- | --- |
| `true` | Jobs and the workspace provisioner. Production and QA need this, because the provisioner is the only path that builds new workspaces there. | Required. |
| `false` | Jobs only. New workspaces are not built by this service. | Must be absent; the Worker refuses to start if it is set. |
| unset | The behaviour from before the switch existed: jobs and the provisioner, every 5 seconds. The Worker logs a line asking for an explicit value. Only for environments configured before the switch; never for a new one. | Required. |

Any other value refuses to start. `WORKSPACE_PROVISIONER_INTERVAL_SECONDS` sets how often the provisioner polls, as a whole number from 5 to 120. Left unset, it is 60 with `true` and 5 when the switch is unset. Production and QA pin 5.

## CI

| Workflow | Trigger | Does |
| --- | --- | --- |
| `ci-server`, `ci-worker` | Pull requests, pushes to `main` | Lint, migrate a fresh database, test, build. |
| `ci-front`, `ci-shared`, `ci-ui`, `ci-mobile`, `ci-e2e` | Pull requests, pushes to `main` | Package checks, run only when the package changed. |
| `ci-security` | Pull requests, pushes to `main` | `yarn npm audit`, constraints, `check-rls`, Docker build. |
| `cd-deploy-tag` | Tags `v*.*.*` | Creates a GitHub release. |
| `publish-image` | Release published, or manual | Runs the image security gate, then, after a reviewer approves the `release` environment, pushes the one gated image (API + Worker) by digest to the private Docker Hub repository `docker.io/adhin007/adolphus`. GHCR is no longer a target. |

A push to `main` may redeploy production if the hosting platform's auto-deploy is on. Keep it off until a release has been prepared with the runbook.

## Release image tags

`publish-image` pushes the one exact gated image (the API and the Worker run the same image with different commands), with digests preserved and no rebuild, under exactly one immutable tag:

- `<full commit sha>`

There is no `latest`, prefix, version or per-architecture tag, and the push refuses a tag that already exists. Releases up to v0.4.0 were two images tagged `api-<sha>` / `worker-<sha>`. The compose files take the one digest as `CREWFLOW_IMAGE_TAG` (named like Twenty's `TAG`, but it accepts only a `sha256:` digest; a plain tag is refused). Deploy by index digest (`docker.io/adhin007/adolphus@sha256:...`) from the release manifest; the tags are labels, not references. See `packages/rab-docker/docs/IMAGE_SECURITY_RELEASE_POLICY.md` section 8.

It always builds from a clean CI checkout, so no local `.env` can reach an image layer.

## Mobile builds

```bash
flutter build apk --release --dart-define=API_URL=https://<your-api-host>/rest/v1
```

Release builds refuse to start without `API_URL`. Android release signing still uses the debug key. Replace it with a real upload key before publishing to Google Play.
