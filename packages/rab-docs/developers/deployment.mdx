## Images and processes

`packages/rab-docker/rab/Dockerfile` (Node 24 Alpine, no browser) builds ONE application image, which the API and the Worker run with different commands; it includes the Worker-only packages, including the native PDF renderer. The image contains no browser: the build fails if Chromium is installed, and the image gate fails if Chromium, Playwright or any library only Chromium pulled in comes back. Both builds fail if Node or libexpat is below the minimum versions in `packages/rab-docker/rab/security-floors.env`.

The three operations commands (`containment:suspend-test-accounts`, `user-session:backfill`, `hws:backfill`) have no service of their own. Like `bootstrap-admin`, each run is a one-off container of the API service (`run --rm --no-deps rab-api node packages/rab-server/dist/command/main.js <command> ...`), from the same image and under the same owner login `crewflow_owner`; any other login is refused. Every run takes the operator label flags (`--operator "<name>"` and `--change-ref <ref>`), the per-run production authority, a host directory for its files and a kept copy of its output. The procedure is in `packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md`, section 7, "Operations commands". There is no separate operations container any more. Of its old variables, the five retired names are refused in every process, and the compose lint refuses the whole `CREWFLOW_OPS_*` / `PG_OPS_*` prefix.

| Service | Command | Database login | Notes |
| --- | --- | --- | --- |
| API | `api-prestart.sh` (then `main.js`) | the one owner login | Migrates on start under the migration lock (O3, like Twenty; approval mode `none`), registers the BullMQ job schedulers, then serves. One instance, deployed stop-then-start. Never bootstraps an admin. |
| Worker | `worker-start.sh` (then `node packages/rab-worker/dist/main.js` under `tini`; the same image as the API) | the one owner login | One non-root process (uid 1000); never migrates and, in the deploy compose files, only consumes the job schedulers the API registers; workspace provisioning runs in-process. The former launcher and its provisioner child are retired (O1). |
| (no release step) | | | O3 removed the one-off `rab-migrate`: the API migrates on start, and the Worker never migrates and only consumes the job schedulers. Back up before every upgrade (`packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md` section 3). |

The database works like Twenty's: the API and the Worker read `PG_DATABASE_URL`, the app login `crewflow_owner`, and only the one-shot `db-setup` service gets an admin login. Three modes, all in `compose.env` (PostgreSQL 16, 17 or 18): (a) the bundled `db` service: `PG_DATABASE_PASSWORD` (its superuser) and `PG_DATABASE_APP_PASSWORD` (`crewflow_owner`); (b) your own database: `PG_ADMIN_URL` (the admin login, `db-setup` only) and `PG_DATABASE_URL` (`crewflow_owner` with a password you choose); (c) your own database with `crewflow_owner` created by hand: `PG_DATABASE_URL` only. In (a) and (b) `db-setup` creates `crewflow_owner` with that password (or sets it) and the one-shot `db-harden` service removes its CREATEROLE in the same deploy, once the schema is complete; in (c) it only checks the login. There are no password or target files. `APP_SECRET` is never part of a database credential. Production refuses the legacy names (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `DATABASE_DIRECT_URL`, `DB_POOL_MAX`) and requires a direct (non-pooled) endpoint with a verified TLS mode: `require`, `verify-ca` or `verify-full`, each checking the full certificate and host name{/* VERIFY */}. For Neon, paste Neon's `neondb_owner` URL as it is into `PG_ADMIN_URL` and set `CREWFLOW_BUNDLED_DB=0`{/* VERIFY */}. Every database variable and the services that receive it: `packages/rab-docker/docs/release/ENV-REFERENCE.md`. The image's default `CMD` is `api-prestart.sh`. With `CREWFLOW_MIGRATE_ON_START=true` (pinned on `rab-api` in every deploy compose file) it runs the short-lived migrate child, which takes the migration lock and checks the target, the deployment identity and the login before applying anything, and records each step in the upgrade logbook. The approval mode is `none` by default; `CREWFLOW_MIGRATION_APPROVAL_MODE=token` is an opt-in that requires the per-release approval token for the exact pending set. Full procedure: `packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md`.

Runtime guards refuse to boot the API or Worker when:

- `DATABASE_URL_UNPOOLED`, `CREWFLOW_MIGRATION_*`, `CREWFLOW_PROVISIONER_DATABASE_URL` or a bootstrap password is present
- in production, a legacy database variable (`DATABASE_URL`, `DATABASE_DIRECT_URL`, `DB_POOL_MAX`) or a libpq variable is set, TLS does not verify the certificate and host name (`disable`, `prefer`, `allow`, `no-verify`){/* VERIFY */}, or the database's deployment identity marker does not match `CREWFLOW_DEPLOYMENT_ENVIRONMENT` / `CREWFLOW_DEPLOYMENT_ID`
- the login is anything other than `crewflow_owner`, or it is a superuser, has BYPASSRLS, CREATEDB or REPLICATION, has CREATEROLE without a valid, unexpired bootstrap mark, or the host is a transaction pooler
- `PG_ADMIN_URL` reaches them (it belongs to `db-setup` only)
- `NODE_ENV=production` is set without `RAB_RUNTIME_ENV=production`

## Deployments

| File | Where | Topology |
| --- | --- | --- |
| `packages/rab-docker/docker-compose.image.yml` | The supported production deployment, with plain `docker compose` (runbook: `packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md`). | `db` (the bundled PostgreSQL 16, not started with `CREWFLOW_BUNDLED_DB=0`), the one-shot `db-setup` and `db-harden`, `rab-api` (migrates on start), `rab-worker` (consume-only, starts after a healthy API) and `rab-redis`, every image pinned by digest. There is no release step. HWS runtime routing is off until the production rehearsal. |
| `packages/rab-docker/docker-compose.production.yml` | The same runtime contract with per-service environment instead of `env_file`, for a platform that shows each variable as a field. Where it differs from `docker-compose.image.yml`, that file wins. OpenShip drops its isolation keys, so OpenShip is not a supported way to run it (`packages/rab-docker/docs/release/OPENSHIP-COMPATIBILITY.md`). | The same services as `docker-compose.image.yml`. |
| `packages/rab-docker/docker-compose.qa.yml` | Local, isolated manual QA | Production's database setup and lifecycle, built from source: the bundled `db` (a verbatim copy of production's), the one-shot `db-setup` that creates `crewflow_owner`, an API that migrates on start and registers the job schedulers, a consume-only Worker, S3 storage through MinIO, HWS off. Loopback-only ports; the database is not published. |
| `packages/rab-docker/docker-compose.yml` | Local development | The same database setup and lifecycle as QA, with local file storage, hot-reload front, and HWS, workspace host routing and the login handoff on, for development only. Fresh, project-scoped volumes; it does not use the previous `rab_devdb_data` volume. |

Workspace provisioning has two paths. The API builds a new workspace's schema right after it commits the workspace row (the server path: `core.provision_workspace`, migration `1786719500000`, called from `workspace-provisioning.service.ts`). The Worker's in-process loop drives any workspace still `CREATING` or `FAILED` to `READY` (see [Background jobs](/developers/background-jobs#workspace-provisioner)), for example when a server-path attempt was deferred.

The operational procedure (per-service environment variable names, migration phases, rollback) is in the production release runbook. Values are never committed.

### Upgrading to 0.6.0

1. **Back up the database before deploying 0.6.0.** Going back to an image older than 0.6.0 (for example R256) is only possible by restoring that backup. Take it as the runbook's mandatory pre-upgrade backup describes (`packages/rab-docker/docs/release/OWNER-LOGIN-DEPLOYMENT.md`, section 3.3) and record where it is.
2. Deploy as usual: `docker compose pull && docker compose up -d`.
3. Check that `/healthz` returns 200 with `upgradeFailed: false`.

Why restoring is the only way back: 0.6.0 adds the upgrade logbook (`core.upgrade_migration`, with its row-level security policies and grants). An older image's start-up security check compares the database with what that older code expects. It sees the logbook as unexpected security objects and refuses to start. This was measured with R256 on a 0.6.0 database. To go back, restore the backup from step 1, then start the previous release with its own compose files.

**Render is retired.** `render.yaml` was removed on 2026-10-23: it described the pre-cutover database roles and migrated at start, which the current guards refuse. Removing the file does not stop any Render service that still exists. Suspend or delete those services in the Render dashboard.

## Environment

Set every required variable in the hosting platform's secret store. See [Environment configuration](/developers/environment-configuration). The API and the Worker need the same application settings, including the same `APP_SECRET`. Both receive the same `PG_DATABASE_URL` (the `crewflow_owner` URL); `PG_ADMIN_URL` goes to the one-shot `db-setup` and `db-harden` services only. The Worker takes no provisioner URL: it provisions in-process on the same owner login (`CREWFLOW_PROVISIONER_*` is refused). There is no `rab-migrate` step and no `.env.migrate`: the API migrates on start under the migration lock.

`CREWFLOW_PROVISIONER_ENABLED` and the other `CREWFLOW_PROVISIONER_*` names are refused on the Worker: provisioning always runs in-process. `WORKSPACE_PROVISIONER_INTERVAL_SECONDS` sets how often it polls, as a whole number from 5 to 120 (default 60); production and QA pin 5. Any other value refuses to start.

## CI

| Workflow | Trigger | Does |
| --- | --- | --- |
| `ci-server`, `ci-worker` | Pull requests, pushes to `main` | Lint, migrate a fresh database, test, build. |
| `ci-front`, `ci-shared`, `ci-ui`, `ci-mobile`, `ci-e2e` | Pull requests, pushes to `main` | Package checks, run only when the package changed. |
| `ci-security` | Pull requests, pushes to `main` | `yarn npm audit`, constraints, `check-rls`, Docker build. |
| `cd-deploy-tag` | Tags `v*.*.*` | Creates a GitHub release. |
| `publish-image` | Release published, or manual | Runs the image security gate, then, after a reviewer approves the `release` environment, pushes the one gated image (API + Worker) by digest to the private Docker Hub repository `docker.io/adhin007/adolphus`. GHCR is no longer a target. |

A push to `main` may redeploy production if the hosting platform's auto-deploy is on. Keep it off until a release has been prepared with the runbook.

## Release image tags

`publish-image` pushes the one exact gated image (the API and the Worker run the same image with different commands), with digests preserved and no rebuild, under exactly one immutable tag:

- `<full commit sha>`

There is no `latest`, prefix, version or per-architecture tag, and the push refuses a tag that already exists. Releases up to v0.4.0 were two images tagged `api-<sha>` / `worker-<sha>`. The compose files take the one digest as `CREWFLOW_IMAGE_TAG` (named like Twenty's `TAG`, but it accepts only a `sha256:` digest; a plain tag is refused). Deploy by index digest (`docker.io/adhin007/adolphus@sha256:...`) from the release manifest; the tags are labels, not references. See `packages/rab-docker/docs/IMAGE_SECURITY_RELEASE_POLICY.md` section 8.

It always builds from a clean CI checkout, so no local `.env` can reach an image layer.

## Mobile builds

```bash
flutter build apk --release --dart-define=API_URL=https://<your-api-host>/rest/v1
```

Release builds refuse to start without `API_URL`. Android release signing still uses the debug key. Replace it with a real upload key before publishing to Google Play.
