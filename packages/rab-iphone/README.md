# Crewflow for iPhone (native, SwiftUI)

Native iOS client for the Crewflow (rab) workforce platform: the Staff app and
the Venue Manager app in one binary, routed by the server-verified identity
(`GET /auth/me`), exactly like the Flutter app in `packages/rab-mobile`.

> **Verification status: source implemented, NOT compiled.** This package was
> written on a Windows host with no Swift toolchain, Xcode or XcodeGen. Nothing
> here has been built, run or tested yet. The first macOS build is expected to
> surface some compile fixes. Treat the test suite as written-not-run.

| | |
|---|---|
| Toolchain | Xcode 15.0+ (Swift 5.9, iOS 17 SDK), Swift language mode 5 |
| Deployment target | iOS 16.0 (the repo states no iOS target: `rab-mobile` has no `ios/` folder) |

## Build and run (macOS)

```bash
brew install xcodegen
cd packages/rab-iphone
cp Config/Local.xcconfig.example Config/Local.xcconfig   # then edit it
./Scripts/generate-project.sh                             # = xcodegen generate
open Crewflow.xcodeproj
```

In `Config/Local.xcconfig` (git-ignored) set:

| Setting | Meaning |
|---|---|
| `DEVELOPMENT_TEAM` | Your Apple Developer Team ID (needed for a device; the simulator can run unsigned) |
| `CREWFLOW_BUNDLE_ID` | The registered bundle id. The committed default `com.example.crewflow` is a placeholder |
| `API_BASE_URL` | Backend base **including `/rest/v1`**. Write `//` as `$(SLASH)$(SLASH)` (`//` starts a comment in `.xcconfig`) |
| `CONSOLE_URL` | Optional: web console (rab-front) for Manager/Admin accounts |

Then choose the `Crewflow` scheme and an iPhone simulator, and press Run.

Command line:

```bash
xcodebuild -project Crewflow.xcodeproj -scheme Crewflow \
  -destination 'platform=iOS Simulator,name=iPhone 15' build

# Unit + UI tests
xcodebuild -project Crewflow.xcodeproj -scheme Crewflow \
  -destination 'platform=iOS Simulator,name=iPhone 15' test

# Unit tests only
xcodebuild -project Crewflow.xcodeproj -scheme Crewflow \
  -destination 'platform=iOS Simulator,name=iPhone 15' \
  -only-testing:CrewflowTests test
```

The UI tests launch the app with `-CrewflowUITesting` (Debug builds only):
in-memory secrets, no biometrics and a placeholder host that is never
contacted, so they need no backend.

## Pointing at a development backend

An iPhone's `localhost` is the **phone itself** (and the simulator's is the
Mac it runs on), never the Windows PC running `rab-server`. Options:

1. **HTTPS dev host (recommended).** Expose the dev API over HTTPS (a dev
   domain, or a tunnel such as `cloudflared`/`ngrok` in front of port 3000)
   and set `API_BASE_URL = https:$(SLASH)$(SLASH)<host>/rest/v1`. Works on
   the simulator and on devices, no ATS exception involved.
2. **LAN, Debug only.** `API_BASE_URL = http:$(SLASH)$(SLASH)192.168.x.y:3000/rest/v1`.
   Debug builds carry `NSAllowsLocalNetworking` (added to the built
   Info.plist by a build phase, Debug configuration only), which permits
   plain HTTP to local-network addresses. The phone must reach the dev
   machine (same Wi-Fi, firewall open on 3000). Release never has an ATS
   exception.
3. **Simulator on the same Mac as the server:** `http://localhost:3000/rest/v1`
   works in Debug.

The server must accept the mobile client: every request sends
`X-Client-Platform: mobile` (required by `/auth/login` and `/auth/refresh`)
and `X-Client-Capabilities: mfa-verify` (this build can finish a 2FA
sign-in; without it an enrolled account gets `CLIENT_UPDATE_REQUIRED`).
A Debug build launched against the `dev-host.invalid` placeholder shows a
"This build is not configured" screen instead of guessing a host.

## Release builds

`Config/Release.xcconfig` includes the git-ignored `Config/Release.local.xcconfig`
(or set the values from CI). The **Verify Release configuration** build phase
fails a Release build unless `API_BASE_URL` is HTTPS, not the placeholder and
ends with `/rest/v1`, the bundle id is not `com.example.crewflow`, and
`CONSOLE_URL` (if set) is HTTPS.

## What is implemented in this package (core)

- Networking (`APIClient`), Keychain token storage, session lifecycle
  (`SessionCoordinator`), biometric unlock, role routing, the design system,
  native sign-in, forgot password, forced set-password, biometric setup/unlock,
  two-factor sign-in (code, recovery code, start again, update required) and
  Profile → Security (2FA on/off, enrolment, recovery codes) —
  `Features/Authentication/TwoFactor`, see
  `docs/account-security/SWIFTUI_REPORT.md` at the repo root (local).
- Staff and Venue Manager shells with real tab screens that state
  "Not yet implemented in this build" (no sample data). Manager/Admin and
  unsupported accounts get the console entry screen, like Flutter.
- See `ARCHITECTURE.md` for the public API and how a feature plugs in, and
  `docs/SECURITY_NOTES.md` for storage, token and logging rules. API and
  parity references live in `docs/API_CONTRACT_MAP.md` and
  `docs/FEATURE_PARITY_MATRIX.md`.
